# 迁移与实施路线

> 从一个 800 余行的单文件程序，迁移到"内核 + 外壳 + 插件"。原则：**每一步都可运行、可回滚，功能不回退**。
> 架构背景见 [README.md](README.md)，接口见 [api-contracts.md](api-contracts.md)。

## 1. 迁移原则

1. **先拆后加**：先让现有功能跑在新引擎上（M0–M1），再引入插件（M3）。
2. **双轨验证**：每个阶段都保留可执行程序，任何一步中断都能交付当前状态。
3. **先内后外**：内置插件先用 API，确认顺手后再对外开放。
4. **性能预算前置**：M1 就建立虚拟端口基准，后续每阶段回归。
5. **接口冻结门槛**：至少 3 个真实插件使用过 → 才宣布 API v1。

## 2. 现有实现 → 目标模块

| 现有位置/能力 | 目标归属 |
|---|---|
| `MainWindow` 中的 `QSerialPort` 成员、`openPort/closePort` | `SerialSession` + `SessionWorker` + `SessionService` |
| `handleReadyRead` / `appendReceiveText` / `maximumBlockCount` | `SessionController` 批处理 + `ui-kit/ConsoleView` |
| `encodeText` / `decodeText` / 编码下拉框 | `Codec` 服务（系统/UTF-8/Latin-1），后续可注册新编码 |
| `sendData` / 定时发送 / HEX 校验 | 命令 `serial.data.send` + 控制台工具栏 |
| DTR/RTS | `ISession::setDtr/setRts` + 控制台状态项 |
| `QSettings` 读写 | `SettingsService`（三层）+ 工作区 `xcom.json`，首次启动迁移 |
| 状态栏计数/状态 | 状态栏贡献项 + 会话统计 |
| `QMessageBox` 错误提示 | `INotificationService` + 会话错误历史 |
| 单窗口单会话 | Shell 多会话标签 + 会话资源管理器 |
| `.pro` / qmake | CMake（多目标、插件、测试、安装布局） |

## 3. 阶段计划

### M0 拆核（约 1.5–2 周）

**目标**：串口逻辑脱离界面，可无硬件测试；功能与现在完全一致。

交付：

- `foundation`、`api`（先落最小接口）、`serial` 三个库骨架；
- `ISerialTransport` + `QSerialPortTransport` + `LoopbackTransport` + `ScriptedTransport`；
- `SerialSession` / `SessionWorker` / `SessionService`（先支持单会话）；
- 现有 `MainWindow` 改为调用 `SessionService`，不再直接持有 `QSerialPort`；
- CMake 构建 + QtTest 单测 + 一个 CI 任务。

验收：

- [ ] 现有全部功能（打开、收发、HEX、时间戳、定时发送、保存）行为不回退；
- [ ] UI 代码中不再出现 `QSerialPort`；
- [ ] `ScriptedTransport` 可在无硬件下跑通接收显示；
- [ ] 单测覆盖状态机迁移、环形缓冲缺口标记、HEX 解析。

风险：串口线程化后关闭时序问题 → 用 5 组开关会话测试覆盖。

### M1 多会话外壳（约 2–3 周）

**目标**：一次开多个串口，界面像 IDE。

交付：

- `SessionService` 多会话、端口独占、会话上限、活动会话、自动重连；
- Shell 主窗口：活动栏 + 侧边栏 + 中央标签页 + 底部面板 + 状态栏；
- 会话资源管理器视图、控制台标签页、布局持久化；
- `ui-kit` 抽出 `ConsoleView`，同一会话支持多视图实例。

验收：

- [ ] 4 个虚拟会话同时收发，切换标签 < 50 ms；
- [ ] 关闭标签页不终止会话（默认），可在设置中改为"关闭即断开"；
- [ ] 重启后恢复布局与（可选的）会话；
- [ ] 拔掉设备：会话置 `Failed`，其他会话不受影响，可重连。

风险：布局状态恢复容易出"幽灵视图" → 视图 id 稳定 + 未知 id 静默跳过 + 日志。

### M2 命令化（约 1.5–2 周）

**目标**：菜单、快捷键、按钮全部走命令注册表。

交付：

- `CommandRegistry`（spec、参数 schema、enablement、执行器、结果）；
- `ContextKeyService` + 上下文键；
- 现有 UI 动作全部改为命令（打开/关闭/发送/清空/HEX/保存/设置）；
- 命令面板（搜索、参数表单、最近使用）；
- 默认键位 + 用户覆盖 + 冲突检测；菜单由贡献数据生成。

验收：

- [ ] 命令面板能执行全部命令，且与按钮行为一致；
- [ ] 新增一个命令不需要改任何界面代码；
- [ ] 键位冲突在设置页可见；
- [ ] 命令执行有超时、取消、错误呈现。

风险：参数与 UI 表单双份实现 → 表单由 schema 生成，禁止手写第二套。

### M3 插件 v1（约 3–4 周）

**目标**：第三方可写插件；内置功能迁成内置插件。

交付：

- `PluginHost`：扫描、manifest 校验、兼容性、依赖、生命周期、订阅回收；
- `plugin-cache.json` 与懒激活；
- 插件管理器视图（状态、错误、启用/禁用、能力、日志入口）；
- 安全模式、工作区信任；
- API v1 冻结（`apiVersion = 1.0`）；
- 内置插件：`sessions`、`console`、`terminal`；示例插件：`checksum`、`modbus`；
- `xcom_plugin_testkit` 与 `hello-world` 模板。

验收：

- [ ] 不修改宿主代码，`hello-world` 插件可注册命令与侧边栏视图；
- [ ] 禁用插件后其命令、视图、设置项立即消失，无残留；
- [ ] 不兼容插件被拒绝并给出具体原因（Qt/编译器/apiHash）；
- [ ] 一个插件 `initialize` 失败不影响其他插件；
- [ ] 契约测试全部通过。

风险：API 设计返工 → 内置插件先行 + 每周一次 API 评审；ABI 问题 → buildStamp 强制校验。

### M4 配置与 CLI（约 2–3 周）

**目标**：配置可协作、可自动化。

交付：

- `SettingsService`（默认/用户/工作区）+ schema + 自动生成设置界面；
- 工作区 `xcom.json`、`.xcom/layout.json`、信任流程；
- 旧 `QSettings` 自动迁移（一次性，带备份标记）；
- `xcom-cli`：`ports`、`send`、`monitor`、`run`、`plugins`、`doctor`；
- 内置命令终端（`com.xcom.terminal`）。

验收：

- [ ] `xcom-cli send --hex` 与 GUI 发送结果一致；
- [ ] `--json` 输出稳定，退出码符合约定；
- [ ] 工作区设置覆盖用户设置，界面标注来源；
- [ ] CLI 不启动 QtWidgets。

风险：两套配置并存期混乱 → 迁移后只读旧库，写新文件。

### M5 脚本与硬化（约 2–3 周）

**目标**：可编程、可诊断、可长期运行。

交付：

- QJSEngine 脚本 API（sessions/commands/settings/events/tasks）；
- `xcom-cli run` 与 GUI `--script`；
- 诊断包（版本、插件、会话、日志路径）、崩溃处理器、结构化日志；
- 性能优化（批量渲染、缓冲、对象复用）、基准回归；
- 代码签名与发布包（`windeployqt` + 插件目录）。

验收：

- [ ] 一段脚本完成"打开→发 AT→断言回包→退出码"的产线冒烟；
- [ ] 4 会话 × 921600 bps 运行 10 分钟：计数一致、内存稳定、UI 可交互；
- [ ] 冷启动 < 300 ms（无第三方插件）；
- [ ] `--safe-mode` 下可正常使用内置功能。

风险：脚本阻塞主线程 → 超时与取消强制；API 面过大 → 只暴露四个命名空间。

## 4. 里程碑依赖

```
M0 ──► M1 ──► M2 ──► M3 ──► M4 ──► M5
 │      │      │      │
 │      └──────┴──────┘   M2 的命令表是 M4 CLI 与 M5 脚本的前提
 └─ 虚拟传输基准贯穿始终（每阶段回归）
```

M3 与 M4 可在人力允许时部分并行（插件管理器 UI 与设置/CLI 相互独立）。

## 5. 工作量估算

| 阶段 | 单人全职 | 说明 |
|---|---|---|
| M0 | 1.5–2 周 | 拆分 + 线程 + 测试 |
| M1 | 2–3 周 | 布局与多会话是主要工作量 |
| M2 | 1.5–2 周 | 命令与面板 |
| M3 | 3–4 周 | 插件宿主与 API 打磨最耗时 |
| M4 | 2–3 周 | 设置/工作区/CLI |
| M5 | 2–3 周 | 脚本、诊断、性能 |
| 合计 | 12–17 周 | 双人并行约 8–12 周 |

## 6. 主要风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Qt 插件 ABI 脆弱（换 Qt 版本即失效） | 第三方插件生态碎片化 | 固定 Qt 版本；`apiHash` + buildStamp 强校验；发布 Qt 运行时；文档明确"升级需重编" |
| 进程内插件崩溃拖垮宿主 | 用户数据丢失 | 安全模式、崩溃处理器、自动保存录制；后续把分析类插件移出进程 |
| 抽象过度导致返工 | 进度延误 | 先用内置插件跑通再冻结；接口只增不改；实验接口标 `experimental` |
| 大流量下 UI 卡顿 | 体验差 | 30 Hz 合并、采样显示、环形缓冲丢旧策略、渲染基准 |
| 停靠布局复杂度失控 | 维护成本高 | 固定 4 个区域 + 标签化，不做任意分屏；视图抽象保留替换余地 |
| 配置/工作区格式反复 | 用户数据迁移麻烦 | 首版即带 `version` 字段与迁移函数 |
| 范围膨胀（市场、多窗口、远程） | 迟迟不能交付 | 非目标清单写进 README，评审时对照 |

## 7. 待确认问题

| # | 问题 | 我的建议 | 影响 |
|---|---|---|---|
| 1 | 只做 Windows，还是兼顾 Linux/macOS？ | 先 Windows，传输层按跨平台抽象 | 影响线程与端口枚举实现 |
| 2 | 是否接受从 qmake 迁到 CMake？ | 建议迁，Qt6 多目标与插件构建更顺 | 影响 M0 工作量 |
| 3 | 插件优先级：C++ 原生优先，还是同时要 JS 插件？ | v1 只做原生；JS 放 M5 | 影响 API 冻结时间 |
| 4 | 是否需要插件市场/在线安装？ | v1 只做本地目录 + "打开插件文件夹" | 省掉签名、下载、版本服务 |
| 5 | 能否接受"插件崩溃 = 主程序崩溃"？ | v1 接受，配安全模式；后续把解析类插件移出进程 | 影响隔离方案与工期 |
| 6 | 是否需要多窗口 / 远程串口？ | 不做，工作区 + 标签页足够 | 避免布局与网络协议复杂度 |
| 7 | 许可证是否允许引入第三方库（如 LGPL 停靠库）？ | v1 不引入，用 QDockWidget | 影响 UI 能力上限 |
| 8 | 现有 `QSettings` 配置是否要自动迁移？ | 要，首次启动迁移并保留备份 | 影响 M4 细节 |

## 8. 完成定义（每阶段通用）

- 编译零警告（MSVC `/W4` 或 MinGW `-Wall -Wextra`）；
- 新增/修改逻辑有单测，CI 通过；
- 有可运行 Demo 或可复现步骤；
- 架构文档与 `docs/architecture/` 同步更新；
- 无 TODO 遗留在公共接口实现里；
- 性能基准不劣于上一阶段。

## 9. 建议的下一步

1. 先确认第 7 节的 8 个问题（尤其是 1、2、3、5）；
2. 把 M0 拆成可执行任务清单（每个任务 ≤ 1 天，带验收点）；
3. 在 `serial` 模块先落 `ISerialTransport` + `Loopback`，用现有界面跑通"伪串口"，再动 UI 结构；
4. 建立 `tests/integration` 的多会话基准，作为后续所有阶段的回归基线。
